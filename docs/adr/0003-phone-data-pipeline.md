# 手机数据：采集端极薄、分析在服务端、经 tailnet 明文传输

手机 App 只做采集与上报（轨迹点进本地队列、就近发出），**停留/行程的切分与判定全部在服务端**做；设备到服务器走 Tailscale 组网，**tailnet 内用明文 HTTP**（WireGuard 已加密），原始轨迹点保留 90 天后只留停留与行程。

## 考虑过的替代方案

- **手机端算好再传**：省流量，但费电、算法迭代要发版、且手机上拿不到完整历史做跨天分析。
- **依赖 GMS 的位置与活动识别 API**：设备无 Google 服务，且这些 API 在国产 ROM 上本来也不稳定。
- **给服务套公网 HTTPS 或走云中继**：多一台机器要维护、多一个公网暴露面；单纯为了"手机能连上"不值得。
- **永久保留原始点**：可回溯性最好，但体积与隐私代价随时间线性增长，而长期有用的信息都在停留与行程里。
- **让模型直接读原始点**：一坨坐标进提示词既贵又答不准，切分是确定性的算法活，不该交给模型。

## 后果

- 采集端必须容忍断网：本地队列 + 失败重试 + 恢复后追平，否则回家路上的数据会丢。
- Android 14+ 禁止从后台启动"定位型"前台服务，所以**手机重启后需要用户打开一次 App** 才能回到 30 秒精度；未打开时只能靠 WorkManager 兜底（最短 15 分钟一次）。
- 国产 ROM（本机是 Redmi/HyperOS）会杀后台，App 必须引导用户开自启动、省电策略无限制、锁定后台任务。
- 明文 HTTP 只允许在 tailnet 内：App 侧用 network security config 限定到那个地址，**不要**全局放开 cleartext。
- 轨迹事件是「会主动打扰用户」的源头，因此事件到动作之间必须过静默时段、去重与频率上限——与主动聊天同一套纪律。

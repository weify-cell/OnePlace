# 微信机器人按「启用意图」在服务启动时自动拉起

机器人有两层控制：**启用意图**（持久，只决定服务启动时是否自动拉起）与**运行态**（本次运行内的手动启停）。服务启动时若启用意图为真就自动拉起；**不看 `NODE_ENV`、不做自动重试**，失败只记日志并把状态交给设置页。关键是第二层：**「停止 Bot」只结束本次运行，不改变启用意图**，所以停止之后再重启服务，机器人会自己回来。同理，启用意图**不限制手动启动**——它不是功能总开关。

## 考虑过的替代方案

- **停止即关闭**（点「停止」同时把启用意图置假）：会让"会话过期了临时重连一下"变成破坏性操作。
- **启用意图兼作功能总开关**（关掉后手动也起不来）：会让"临时关掉自动拉起、现在手动试一下"变成不可能；拦截只属于自动启动这一处。
- **只在生产模式自动拉起**（判断 `NODE_ENV === 'production'`）：本项目的日常运行方式就是开发模式（`tsx watch`），判环境等于让这个功能永不生效。**不要"补上"这个看似缺失的判断。**
- **启动失败自动退避重试**：凭证失效只能人工扫码，自动重试会把"需要你扫码"掩盖成"系统在自己恢复"。
- **把机器人失败当成服务启动失败**：机器人是附加功能，任何情况下都不该影响 HTTP 服务起来。

## 后果

- 会话过期时不自愈：停掉那个已死实例的轮询、把登录状态置为"会话过期"，由设置页引导人工重新启动；此后台子系统仍继续运行。不自愈就不能不暴露，否则这是个看不见故障的黑盒。
- 停机期间的"到点就该生成"作业（日报、记忆整理）不会补跑，与既有的窄窗口问题同源。
- 开发期每次保存后端代码都会拉起机器人并开始回真实消息——关掉它的手段是设置页的启用意图开关。

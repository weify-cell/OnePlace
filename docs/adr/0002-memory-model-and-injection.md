# 记忆分「状态型 / 事件型」两类，退场一律归档而非删除

记忆按"这条信息会不会被新值取代"分成两类：**状态型**（进度、约定、偏好）在新值到来时被**取代**，旧值归档；**事件型**（某时发生了什么）只随时间**退场**。退场统一是归档，不是物理删除——判据里的"会遗忘"在系统里的表现应当是不再出现，而不是数据消失。注入也不再是"近 30 天全量塞进提示词"（实测每消息 169 条 / 12,897 字符），而是压缩后的状态型最新值；按语义找旧记忆交给模型自己调检索工具。

## 考虑过的替代方案

- **每轮按当前对话检索 top-N 再注入**：会让每条消息多一次 embedding 加一次向量查询（延迟与费用），而"该不该捞那条旧记忆"本来就该由模型决定。
- **物理删除过期记忆**：不可逆；判据只要求"退场"，归档同样让它不再被检索到，还能回溯。
- **让模型把历史记忆归并重写一遍**：等于让模型重写用户的历史记忆，跑偏不可逆，收益不确定。
- **给记忆做完整 CRUD 界面**：写操作立刻带来新的同步问题（改了内容要不要重算向量、归档了向量删没删），先用只读可见性回答"它到底记了什么"。

## 后果

- 归档必须**同时删掉向量库里的向量**：写入端只增不删是这套代码里已经出现过两次的缺陷类型（笔记的分块残骸、软删笔记的孤儿向量），别再犯第三遍。
- 状态型记忆的"最新值"依赖模型写入时稳定输出主题键。这是新契约，必须由 spec 定死，否则各工单会各写一套。

## 修订（2026-10-12）：允许给历史记忆补标注

**本文原先那条"未分类的历史记忆（旧数据）不回填"已被推翻**——用户在看清单个后果后明确选了"补标注"（见 `.scratch/memory-system/issues/04-compressed-injection.md` 的"必须先决定的事"）。推翻理由是实测：修正前 205 条历史记忆全部未分类，而没有任何路径能让它们进入压缩摘要（整理提示词写着"请勿重复抽取"，而重复写入命中未归档的同内容行只返回 duplicate），于是"会提炼"的注入一半等于没生效。

因此：

- **模型可以给既有记忆补上类型与主题**，只补元数据，不改内容与日期、不新增行；补标注走正常写入路径，工具答复写明"已给已有记忆补上类型与主题"。
- "不参与压缩摘要、不参与淘汰"仍然适用于**没被标注的**那些未分类行。
- 这条修订也暴露了原文一句措辞不准：未分类行其实**不会**"随时间自然退场"（退场只处理事件型），它们只是不再参与注入与取代。以代码为准。

### 取代的规则改为"按日期最新者胜"

同用户同主题的多个活跃状态值，保留 `(memory_date, id)` 最大的那条，其余归档。

这与原措辞"同一用户同一主题的**新**状态型记忆写入时，旧值被归档"不同：补标注进来的行通常**很旧**，不能因为它刚被认领就把更新的当前值挤下去（实测第一遍补标注后，同一本书的进度出现过"旧的被当成当前值"）。

代价是：一次**写入日期偏旧**的正常写入（例如整理补跑写到几天前）可能当场就被归档。这是有意的——它确实比库里已有的值旧——但因此**必须如实告知调用方**（工具答复会写"同主题已有更新的值，本条未成为当前状态"），不能只说"已记住"。

### 已知弱点：主题键由模型产出，实测并不稳定

本文原已把这列为新契约并说"必须由 spec 定死"，但**证据表明光靠提示词约束不够**：一次性补标注跑了三遍，模型判为"当前状态"的条数分别是 23 / 7 / 15，主题键也每次不同（同一本书落在"阅读任务:习惯的力量"与"阅读进度:习惯的力量"两个键上）——取代靠键的**完全字符串相等**，拼法不一致就不会触发。因此 `queryCurrentStateMemories` 里"不需要按主题去重"这个前提并不牢靠。后续若要收紧（例如让注入不依赖分类质量、只取最近 N 条活跃状态值），应新开工单，不在本次修订里改。
